# 面试讲述稿

## 30 秒介绍

这个项目是一个短视频平台数据库系统，最开始是数据库课程设计，后来我把它进一步工程化：后端用 Flask，数据库用 MySQL，业务上覆盖用户、视频、点赞、评论、关注、私信和标签。优化重点不只是做页面，而是围绕数据库设计、分层架构、权限安全、索引优化、并发实验、GitHub Actions CI 和 Docker Compose 一键启动环境，把它整理成一个更接近真实后端项目的作品。

## 1 分钟介绍

项目里我设计了 9 张核心业务表，通过主键、外键、唯一约束和 CHECK 约束保证数据一致性。例如点赞表用 `(user_id, video_id)` 唯一约束避免重复点赞，视频和用户使用 UUID 避免并发插入时 ID 冲突。

后端方面，我把原本单文件 Flask 应用重构成 `routes / services / dao` 三层结构。`routes` 负责请求和模板渲染，`services` 放密码校验、权限判断、作者校验等业务规则，`dao` 负责 SQL 和存储过程调用。

安全和优化方面，我把数据库配置改成环境变量，密码改成 Werkzeug 哈希存储，管理员权限改成基于 `users.role` 字段判断；同时为作者查询、领域筛选、时间线排序、热门视频查询设计了二级索引和复合索引，并写了并发插入/查询脚本，用 QPS、平均延迟和 P95 延迟分析索引优化效果。

## 面试官可能追问

### 为什么要做分层重构？

原始课设代码容易把路由、SQL、权限判断和业务逻辑都写在一个文件里。这样功能多了以后不好维护，也不好测试。我把它拆成 `routes / services / dao` 后，权限校验和业务规则可以单独测试，SQL 也更集中，后续扩展功能更清晰。

### 为什么用 UUID？

原始项目里常见的做法是用 `COUNT(*)` 或手动编号生成 ID，这在并发插入时可能产生重复 ID。UUID 虽然比自增 ID 更长，但在这个项目里可以简化并发安全问题，也方便后续做分布式扩展的讨论。

### 点赞如何防重复？

点赞表对 `(user_id, video_id)` 建了唯一约束。即使两个请求同时到达，数据库层也能保证同一个用户不能重复点赞同一个视频。应用层捕获唯一约束异常，给用户返回已经点赞的提示。

### 索引怎么设计？

我先根据业务访问路径设计索引，而不是盲目加索引。比如作者主页需要 `author_id`，领域筛选需要 `field_id`，时间线需要 `upload_time`，热门视频需要 `(author_id, likes_count, upload_time)` 这样的复合索引。索引能提升读性能，但会增加写入维护成本，所以我也写了插入和查询压测脚本，用数据比较读写取舍。

### 项目里安全做了什么？

主要做了四点：数据库连接信息从环境变量读取；密码用 Werkzeug 哈希存储；管理员权限由 `users.role` 字段控制；删除用户这种破坏性操作改成 POST，并禁止管理员删除当前登录账号。

### 这个项目还有哪些可以继续优化？

可以继续加 CSRF 防护、分页查询、连接池，以及更完整的集成测试。如果要更接近生产系统，还可以把角色权限扩展成 RBAC 表结构，把视频存储接到对象存储，把日志和错误监控接入统一平台。
